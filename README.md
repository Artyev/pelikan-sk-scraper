# Pelikan → Teatro Argentina → Supabase

Python 3.11+ scraper для прямых рейсов в Рим (FCO и CIA) к **NON POSSO NARRARE LA MIA VITA**, Teatro Argentina, **18.02.2027, 20:00 Europe/Rome**. Время спектакля взято из задания. Театральные билеты этот проект не собирает.

## Бесплатный удалённый запуск: GitHub Actions

Подготовлен `.github/workflows/pelikan.yml`: GitHub запускает временную Linux-машину дважды в день, скрапер пишет в Supabase. Компьютер пользователя может быть выключен. Публикация репозитория и запуск workflow ещё не выполнены.

1. Создать репозиторий GitHub и загрузить код, включая скрытую папку `.github/`. Не загружать `.env`, `.venv` и `data/`. Сохранять настройки и ключи через интерфейс GitHub; локальный `.env` в Actions не нужен.
2. Применить обе SQL-миграции в Supabase, как описано ниже.
3. В GitHub открыть **Settings → Secrets and variables → Actions → Secrets**. Добавить repository secrets `SUPABASE_URL` и `SUPABASE_SECRET_KEY`.
4. В **Actions → Pelikan flight collection → Run workflow** выбрать `check`. Это один реальный поиск VIE и проверка записи в Supabase. Убедиться, что job успешен и записи появились в базе.
5. В **Settings → Secrets and variables → Actions → Variables** добавить `CAMPAIGN_START_UTC`: время начала, например `2026-10-05T00:00:00Z`. Задать актуальную дату и затем **не менять её** в течение кампании. Срок — 21 день из `config.json`. Каждый новый runner читает одну и ту же дату, поэтому кампания не перезапускается каждый день.
6. Workflow должен находиться в **default branch** репозитория, а Actions должны быть разрешены. Автоматические запуски: **06:37 и 18:37 UTC**. Это интервал 12 часов; изменение `collection_interval_hours` в config не меняет cron в YAML. `collect` вручную запускает дополнительный полный проход внутри окна; для обычной работы он не нужен.

[GitHub Free](https://docs.github.com/en/billing/concepts/product-billing/github-actions) включает 2 000 минут в месяц для приватных репозиториев и 500 МБ хранения артефактов (общий бюджет аккаунта, не только этого проекта). Для публичного репозитория стандартные GitHub runners бесплатны без квоты минут; код и логи тогда публичны. Secrets остаются отдельно от кода. Большие платные runners здесь не используются.

На один job задан предел **45 минут**: 42 плановых прохода занимают максимум 1 890 минут, если все попали в один расчётный месяц. Проверки, повторы, запуски вне окна и другие проекты также расходуют минуты. Через 40 минут длительная операция прерывается, чтобы успеть сохранить незагруженные снимки; полный проход 90 поисков на GitHub ещё не измерен, медленный сайт может привести к неполному проходу и ошибке job. Не включать платное превышение квоты; без платёжного метода GitHub блокирует использование после исчерпания включённого лимита. Это бесплатный вариант **в пределах квот**, а не гарантия доступности без ограничений.

Поскольку диск runner временный, здесь не используется локальный `tick` и cron-скрипт VPS. Неотправленные снимки сохраняются отдельным сжатым Actions artifact `pelikan-pending-v1-...` на **30 дней**. В начале следующего запуска они отправляются повторно. Артефакт удаляется только после подтверждения всех снимков Supabase; частично доставленные снимки можно отправлять повторно без дублей. В облаке не создаются новые копии старых артефактов. Исходные raw успешно загруженных снимков в этом режиме не архивируются — остаются компактные записи Supabase.

При длительной недоступности/заполнении Supabase артефакты накапливаются и расходуют отдельный лимит GitHub. Если загрузка artifact не удалась, срок хранения истёк или runner аварийно потерян, локальные данные могут быть утрачены; это не постоянный резервный диск. Ошибки workflow нужно отслеживать через уведомления GitHub Actions. `sync` в Run workflow позволяет вручную доставить оставшиеся артефакты даже после конца кампании. После финальной доставки можно отключить workflow через меню Actions; данные в Supabase сохраняются.

[GitHub предупреждает](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule), что запуски по расписанию могут задерживаться или пропускаться под нагрузкой. Первую проверку необходимо выполнить с GitHub: успешный локальный тест не подтверждает доступность Pelikan с IP GitHub. При блокировке скрапер остановится и покажет ошибку.

## Что реализовано

- 30 аэропортов × 16–18 февраля = 90 поисков за запуск; вылет в локальную дату аэропорта. Один взрослый, экономкласс, в одну сторону, EUR.
- Реальные JSON-запросы веб-приложения Pelikan: анонимная сессия, серверный фильтр ZERO, пагинация по 10 предложений и дополнительная проверка каждого сегмента. Пересадки, технические остановки и неавиационные сегменты исключаются.
- На 18 февраля допустим прилёт до **17:00 по Риму** включительно. 180 минут — настраиваемый плановый запас на выход из аэропорта, трансфер и вход в театр, не гарантия отсутствия задержки. Поздние прямые рейсы сохраняются с `eligible_for_event=false` для анализа.
- История наблюдений в Supabase. Снимок одного поиска загружается атомарно через RPC; повторная отправка того же UUID не дублирует строки.
- JSON outbox на диске сохраняется **до** отправки. При отказе Supabase файл остаётся для `sync`, остальная часть прохода собирается локально; отправленные снимки перемещаются в `sent/`.
- Ошибка сайта, незавершённая пагинация и отсутствие предложений имеют разные статусы. Отсутствие в выдаче не считается доказательством, что рейс распродан.
- Последовательные запросы с паузой 5 секунд; до 3 попыток при сетевых ошибках/5xx. При 401/403/429 запуск останавливается.

## Быстрый запуск

Во время проверки используются только стандартные библиотеки Python; установка пакета необязательна.

```bash
python3 -m pelikan_tracker plan
python3 -m pelikan_tracker run --origin VIE --date 2027-02-18 --local-only
```

Локальный режим делает настоящий запрос Pelikan и сохраняет снимок в `data/outbox/`. Он ничего не загружает в базу. Полный проход:

```bash
python3 -m pelikan_tracker run --local-only
```

Установка CLI в отдельное окружение, если нужна:

```bash
python3 -m venv .venv
.venv/bin/pip install -e '.[dev]'
.venv/bin/python -m pytest -q
```

## Supabase

1. Выполнить по порядку обе миграции из `supabase/migrations/`: `202610040001_flight_tracker.sql`, затем `202610040002_storage_budget.sql`. Если первая уже применена, выполнить только вторую. Вторая добавляет контроль объёма без удаления существующих записей.
2. Скопировать `.env.example` в `.env` и заполнить URL проекта и **backend secret key** из настроек Supabase. Ключ не нужно присылать в чат. Поддерживается также legacy `SUPABASE_SERVICE_ROLE_KEY`.
3. Экспортировать окружение и запустить скрапер:

```bash
set -a
source .env
set +a
python3 -m pelikan_tracker run --origin VIE --date 2027-02-18
python3 -m pelikan_tracker sync
python3 -m pelikan_tracker run
```

Программа сама не читает `.env`: его загружает shell или ваш runner. `run` без `--local-only` требует настройки Supabase до первого поиска. `sync` отправляет накопленные снимки без новых запросов Pelikan.

Таблицы отделены от театрального скрапера: `flight_searches` и `flight_observations`. Для объединения используйте согласованный с командой `event_id` из `config.json`. Внешний ключ на таблицу событий не навязан, поскольку её схема ещё неизвестна.

RLS включён, доступа `anon`/`authenticated` нет. Запись разрешена серверному `service_role`; views также доступны backend. Политики чтения для вашего приложения команда добавляет под свою авторизацию. Ключ хранится только в окружении backend, не в клиентском приложении. [Документация ключей Supabase](https://supabase.com/docs/guides/getting-started/api-keys).

```sql
-- Подходящие варианты из последней попытки каждого поиска, дешёвые сначала.
select origin, destination, departure_at, arrival_at,
       marketing_carrier, flight_number, price_amount, currency, observed_at
from public.latest_event_flights
order by price_amount;

-- Покрытие/ошибки нужно смотреть отдельно, чтобы отличать их от отсутствия рейсов.
select origin, departure_date, status, error, observed_at
from public.flight_searches
order by observed_at desc;

select * from public.flight_price_history order by observed_at desc;
```

`timestamptz` хранит момент времени; для отображения Рима используйте `AT TIME ZONE 'Europe/Rome'`. В JSON сохранены ISO 8601 смещения каждого аэропорта. Время наблюдения — UTC.

## Собираемые данные и их смысл

| Поле | Значение |
|---|---|
| `price_amount`, `currency` | Цена предложения в выдаче для одного взрослого. Доплаты при оформлении не проверяются. |
| `available` | Флаги доступности предложения и выбранного перелёта. Не резервирует билет. |
| `seats_available` | `null`: точный остаток мест отсутствовал в проверенном поисковом ответе. |
| `flight_key` | Маршрут, локальный вылет, маркетинговый перевозчик и номер рейса. |
| `fare_key` | Ключ рейса + класс, известное имя тарифа и информация о багаже. |
| `offer_key` | Ключ тарифа + цена и доступность; используется внутри одного снимка. |
| `operating_carrier` | Фактический перевозчик, когда указан. Codeshare сохраняется отдельным предложением. |
| `cabin_baggage`, `checked_baggage` | Только данные сегмента. Пустой массив преобразуется в `null`, а не «багажа нет». |
| `fare_name`, `aircraft` | Имя тарифа, тип самолёта, если возвращены. |
| `eligible_for_event` | Проверка прилёта с заданным запасом. |
| `minutes_until_event` | Минуты между посадкой и началом спектакля. |
| `search_url` | Повторяемая ссылка поиска, без временного токена сессии. |
| `raw` | Полные данные сегмента остаются в локальном outbox/sent. В Supabase новые записи содержат `{}` для экономии места. |

Неизвестное имя тарифа ограничивает точность сравнения: `change_eur` показывает изменение минимальной сопоставимой котировки, а не гарантированно идентичного набора услуг. Изменение расписания создаёт новый `flight_key`.

## Регулярный мониторинг

Настроена кампания **21 день, один проход раз в 12 часов**. Это 42 прохода по 90 поисков. Используйте `tick`: первый вызов фиксирует начало и конец кампании в `data/campaign.json`, последующие запускают сбор только в очередном 12-часовом интервале. После 21 дня новые поиски не начинаются; уже начавшийся запрос может закончиться после границы. Собранная история не удаляется.

Расписание на сервере **ещё не установлено**. Скрипт `scripts/scheduled_run.sh` загружает `.env`, отправляет ожидающие снимки через `sync`, затем вызывает `tick`. Неудачная отправка не мешает очередному сбору сохранять данные локально. Проверка каждый час не означает сбор каждый час: `tick` выполняет проход раз в 12 часов. Пример crontab (заменить путь на абсолютный путь проекта, `.env` должен быть доверенным локальным файлом):

```cron
17 * * * * /bin/bash /absolute/path/to/project/scripts/scheduled_run.sh >> /absolute/path/to/project/data/cron.log 2>&1
```

Заранее создать `data/`; пути с пробелами в crontab заключить в двойные кавычки. Скрипт использует `.venv/bin/python`, если окружение существует, иначе `python3` из PATH. На сервере нужны Python 3.11+, работающая служба cron и `flock` (util-linux). Внешняя блокировка охватывает и `sync`, и `tick`; встроенная блокировка дополнительно предотвращает перекрытие `tick` на одном сервере. `tick` рассчитан на Linux и постоянный диск. Не удалять файл состояния при перезапусках и не запускать независимые копии кампании на разных серверах. Продолжительность и интервал фиксируются при первом вызове; изменение config не перезапускает начатую кампанию. Пропущенные интервалы после отключения сервера не восполняются фиктивными историческими снимками. При аварии посреди прохода интервал считается использованным, следующий — по расписанию.

`run` остаётся ручным запуском и **не ограничен** 21-дневной кампанией. `sync` запускать после восстановления Supabase; он доставляет прежние снимки с прежним временем, в том числе после завершения кампании. Outbox, `sent/` и состояние должны лежать на постоянном диске. Логи и архивы требуют вашей политики хранения.

## Бюджет Supabase Free на три недели

[Supabase Free ограничивает размер базы 500 МБ](https://supabase.com/docs/guides/platform/database-size). Учитываются таблицы и индексы; файлы Storage — отдельная категория. Поэтому 500 МБ нельзя полностью отдать JSON авиабилетов. Настройки учитывают возможность совместного проекта с театральным скрапером.

Предварительный расчёт при 2 проходах в сутки, 90 поисках за проход и условных **2 КБ на наблюдение с индексами + 2 КБ на запись поиска**:

| Среднее число предложений на поиск | Записей предложений за 21 день | Оценка таблиц авиаскрапера |
|---|---:|---:|
| 6 | 22 680 | 52,92 МБ |
| 20 | 75 600 | 158,76 МБ |
| 30 | 113 400 | 234,36 МБ |
| 50 | 189 000 | 385,56 МБ — выше бюджета |

Это сценарии, не измерение PostgreSQL и не гарантия: число предложений и размер строк меняются. В проверенном примере компактный JSON составляет около 960 байт на предложение против 1530 с raw, но байты JSON не равны размеру строк и индексов в базе. После первого полного прохода нужно проверить фактический рост и количество предложений.

```bash
python3 -m pelikan_tracker estimate --offers-per-search 20
python3 -m pelikan_tracker usage
```

Вторая миграция проверяет размер **перед каждой новой записью снимка**, в том числе при `sync`. Пороги: **250 МБ для таблиц авиаскрапера с индексами** и **400 МБ для всего кластера баз проекта**. Дополнительно учитывается запас 2 МБ плюс оценка размера следующего снимка. Значения в SQL указаны в десятичных байтах. `usage` возвращает реальные `database_bytes` и `flight_bytes`.

При достижении порога RPC возвращает `null`, ничего не записывая. Скрапер продолжает текущий проход локально; последующие снимки остаются в outbox до появления места и запуска `sync`. Отправка полных raw-данных в облако отключена и в Python, и в RPC. Уже существующие строки не переписываются. Идемпотентный повтор уже загруженного снимка допускается даже у порога.

Это защита записей **этого** скрапера, а не ограничитель всех записей проекта: театральный скрапер и системные таблицы могут продолжить рост. Для гарантированного общего бюджета команда должна контролировать их объём тоже. При нехватке места полная история останется локально, но все 21 день могут не поместиться в Supabase. Ничего автоматически не удаляется и предложения не отбрасываются ради экономии.

Миграция и контроль размера подготовлены, но пока не проверены в вашем Supabase без подключения к проекту.

## Ограничения и проверка

Адаптер основан на реально проверенном веб-клиенте Pelikan, а не документированном партнёрском API. `desktop-docker/config.json` сообщает актуальный API URL и валюту; изменение контракта может потребовать исправления адаптера. В `robots.txt` Pelikan путь `/gf1/` указан как Disallow; для регулярного промышленного сбора согласуйте доступ с владельцем сайта. CAPTCHA, ограничения доступа и авторизацию скрапер не обходит.

Тестовый ответ VIE → ROM на 18.02.2027 сохранён в `tests/fixtures/` в сокращённом виде, без сессионных токенов. Это исторический fixture, **не актуальное предложение**. Тесты проверяют часовые пояса, границу прилёта, исключение пересадок, корректность цены, пагинацию и повторную доставку. Подключение к вашему Supabase и применение миграции требуют настроек проекта; без них облачная запись не проверена.

Контрольный запуск готового CLI 04.10.2026: `python3 -m pelikan_tracker --outbox data/live-check run --origin VIE --date 2027-02-18 --local-only` завершился успешно — 6 прямых предложений экономкласса, из них 1 соответствует запасу времени до спектакля. Полный проход 90 поисков ещё не выполнялся; это проверка адаптера на одном маршруте. Обнаруженные предложения и цены могут измениться.

## Что полезно добавить следующим

1. Итоговая стоимость с нужным багажом, местом и условиями тарифа — отдельное чтение деталей выбранного предложения, с новой проверкой контракта.
2. Цена и длительность трансфера FCO/CIA → театр; сейчас вместо расчёта маршрута используется заданный запас.
3. Ночёвки и ориентировочная цена гостиницы для прилёта 16–17 февраля: более дешёвый перелёт может дать более дорогую поездку.
4. Сигналы о снижении цены, появлении нового предложения и исчезновении из полной выдачи. Исчезновение не равно отмене или распродаже.
5. Общая стоимость «перелёт + театр + трансфер + проживание» после согласования `event_id` и схемы с театральным скрапером.
